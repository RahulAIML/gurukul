# ADR-006: Thin repositories, no generic repository abstraction

**Status**: Accepted
**Date**: This design phase

## Context
SRS §8 specifies Controllers → Services → Repositories → MongoDB but doesn't define how "thick" or generic the repository layer should be. See `DESIGN_PHASE_REVIEW.md` D3.

## Decision
One repository per Mongoose model, exposing typed CRUD + query functions. No generic base-repository class, no swappable-datastore interface/implementation split. The sole justification for having a repository layer at all is that it gives services a mockable seam for unit testing without a real database connection — not "layering for its own sake."

## Consequences
- Avoids the abstraction-for-its-own-sake anti-pattern the brief explicitly warns against.
- If MongoDB is ever replaced or a second datastore introduced (not currently anticipated), repositories would need to grow an interface layer at that point — deferred until there's a real second implementation to justify it.
