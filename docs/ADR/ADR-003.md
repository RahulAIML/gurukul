# ADR-003: Formalize the Category Engine via a CategoryConfig contract

**Status**: Accepted
**Date**: This design phase

## Context
SRS §3 states categories "inherit platform but maintain independent logic" and that future categories should be addable "without platform rewrite," but doesn't specify the mechanism. Without a concrete contract, "domain-driven design" (SRS §14's stated risk mitigation for category-expansion complexity) is aspirational, not actionable — see `DESIGN_PHASE_REVIEW.md` gap R1.

## Decision
Introduce a `CategoryConfig` interface (nav entries, onboarding steps, recommendation engine, AI persona reference, route base paths) as the single structural point where the platform "knows" a category exists. Platform code (category selector, nav shell, admin, route mounting) reads a registry of `CategoryConfig` objects generically; it never contains category-name conditionals. Full detail: `CATEGORY_ARCHITECTURE.md`.

## Consequences
- Adding English/Cricket later is a registration exercise (new config + new self-contained module) rather than a platform-core change.
- Slightly more upfront structure than the simplest possible Gym-only implementation — justified because the SRS's own stated goal (multi-category platform) requires it; this is not speculative abstraction, it's the specific risk SRS §14 already named.
